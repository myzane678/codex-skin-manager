# 主题重命名设计

## 目标

让主题库中的任意已安装主题都能直接修改显示名称。重命名必须同时更新运行时清单、主题库元数据和可导出主题包，确保重启、启用和再次导入导出后名称始终一致。

## 范围

- 支持导入主题和从图片创建的主题。
- 支持重命名当前启用主题；不改变其 ID、版本、启用状态或已运行的样式。
- 本次不支持修改作者、描述、ID、版本、颜色或其他主题配置。
- 不改变已完成的图片选择和拖放创建流程。

## 用户流程

1. 用户在主题卡片上点击“重命名”图标。
2. 卡片原名称位置切换为文本输入框，预填当前名称，并显示“保存”和“取消”操作。
3. 用户输入去除首尾空白后长度为 1 至 80 个字符的新名称；空白或超长名称不能保存。
4. 保存期间卡片操作和重复提交禁用；成功后主题库和当前主题侧栏立即显示新名称。取消则不产生任何文件或状态改变。
5. 当前启用主题可直接重命名；重新打开管理器、继续启用，或导出再导入后均显示新名称。

## 架构与数据一致性

### 受控 IPC

- 新增 `theme:rename`，参数是 `ThemeIdentity` 与 `name`。
- 主进程仅接受对象形状正确、`id` 与 `version` 为非空字符串、且名称 `trim()` 后长度为 1 至 80 的请求；其他输入抛出 `IPC_ARGUMENT_INVALID`。
- preload 仅暴露 `renameTheme(identity, name)`；渲染进程不得读取安装目录、修改清单或创建 ZIP。

### 服务层

- `ManagerService.renameTheme(id, version, name)` 先定位已安装主题，再委托存储层执行持久化更新，最后返回最新 `ManagerSnapshot`。
- 主题 ID、版本、来源、资源文件、资源哈希与当前启用配置保持不变。
- 主题视图仍从安装元数据读取名称；因此重命名成功的 snapshot、重启后的枚举和当前主题侧栏保持一致。

### 原子更新

主题安装目录必须将下列内容作为一个一致性单元更新：

1. `manifest.json` 的 `name`。
2. `.installed.json` 的 `name`。
3. `package.codextheme` 内 `manifest.json` 的 `name`，其资源内容与 SHA-256 声明保持原样。

存储层先读取并验证当前 manifest 和安装元数据，基于现有受控资源重建新的临时 `.codextheme` ZIP，再将新 manifest、元数据和 ZIP 写入同目录临时文件。只有所有临时文件准备成功，才用 `rename` 逐项替换正式文件。

若准备阶段失败，不写入正式文件。若替换阶段失败，存储层必须尽力将已经替换的文件恢复为原始字节，并抛出错误；调用方不返回成功 snapshot。这样不会把“主题库名称、运行时名称、导出包名称”留在不同版本。

## 界面

- `ThemeCard` 在既有启用、导出和删除图标旁添加带 tooltip 的重命名图标。
- 编辑状态使用卡片内联输入框，不新增页面、弹窗或额外主题管理入口。
- 点击保存时调用现有 App 的统一异步操作包装器，以便沿用全局 busy 和错误提示行为。
- 点击取消、按 Escape，或保存失败后，输入状态回到当前已保存的主题名称；保存失败不改变列表显示。

## 测试与验收

- 服务层测试：成功重命名后，`manifest.json`、`.installed.json`、导出的 `package.codextheme` 都含新名称；导出包能在新主题目录导入并显示新名称。
- 服务层测试：当前启用主题重命名后仍保持启用；空白、超长、找不到的主题拒绝且不修改任何持久化文件。
- IPC 测试：合法身份与名称转发给服务层；非法身份、空白名称和超长名称返回 `IPC_ARGUMENT_INVALID`。
- 渲染测试：打开编辑、预填名称、非法名称不能提交、保存回调参数正确、取消和 Escape 恢复显示、busy 时禁用操作。
- 完整验证：`npm run typecheck`、`npm run lint`、`npm test -- --run`、`npm run package` 和 `git diff --check`。
